# API Design — IT Ticketing System

## 1. General API Conventions

Base URL:

```text
/api/v1
```

Authentication:
Session rule:
Each successful login creates an AuthSession record.
The generated JWT must include a session identifier.
For every protected request, the backend validates both the JWT and its related active session.
If the session is revoked, expired, or not found, the request must be rejected with 401 Unauthorized.
Logout revokes the current session.

```http
Authorization: Bearer <access_token>
```

Date format:

```text
ISO 8601
Example: 2026-06-29T10:30:00Z
```

Pagination query:

```text
?page=1&perPage=10
```

Standard success response:

```json
{
  "success": true,
  "data": {}
}
```

Standard paginated response:

```json
{
  "success": true,
  "data": [],
  "meta": {
    "page": 1,
    "perPage": 10,
    "total": 120,
    "totalPages": 12
  }
}
```

Standard error response:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "fields": {
      "username": ["Username is required"]
    }
  }
}
```

Common status codes:

```text
200 OK
201 Created
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Validation Error
500 Internal Server Error
```

# 3. Access Rules Used by APIs

## Support Read Scope

A Support can read a ticket if:

```text
ticket.assignedTo.id == currentSupport.id
OR
support has VIEW_TICKET permission AND ticket.department.id is in support.departments
```

## Support Action Scope

A Support can perform actions only if:

```text
ticket.assignedTo.id == currentSupport.id
AND support has the related operation permission
```

Examples:

```text
Reply requires:
assigned_to_me + REPLY_TICKET

Change status requires:
assigned_to_me + CHANGE_TICKET_STATUS

Change department requires:
assigned_to_me + CHANGE_TICKET_DEPARTMENT

Change assignment requires:
assigned_to_me + CHANGE_TICKET_ASSIGNMENT
```

Important:

```text
VIEW_TICKET never allows reply, status change, department change, or assignment change.
```

## Support Overview Scope

```text
Support overview is calculated only from tickets assigned to that Support.
VIEW_TICKET has no effect on overview statistics.
```

## 4.6 Update Auth Me / Profile

```http
PATCH /auth/me
```

Role:

```text
Authenticated User / Support / Admin
```

This endpoint updates only the authenticated user's own profile.
To update the profile image, the client must upload the image first with `POST /files`, then send the returned file `id` as `profileImageFileId`.

Request body:

```json
{
  "name": "Ali Reza Mohammadi",
  "username": "ali_reza",
  "profileImageFileId": 501
}
```

All request fields are optional, but at least one field must be provided.

Rules:

```text
name and username update the authenticated user's own user record.
profileImageFileId must belong to the authenticated user.
profileImageFileId must reference a PNG or JPG file uploaded through POST /files.
profileImageUrl is stored as /files/{fileId}/download.
Changing profile fields does not invalidate active AuthSessions.
Changing profile fields does not change role, permissions, departments, availabilityStatus, password, or JWT payload structure.
```

Response for User:

```json
{
  "success": true,
  "data": {
    "id": 10,
    "name": "Ali Reza Mohammadi",
    "username": "ali_reza",
    "role": "USER",

    "lastLoginAt": "2026-06-29T10:00:00Z"
```

# 16. JWT Validation Rule

Every protected endpoint must validate:

```text
1. Token exists
2. Token signature is valid
3. Token is not expired
4. User exists and is active
5. token.iat must be after user.password_changed_at
```

If Admin changes Support password:

```text
user.password_changed_at is updated.
Any old token issued before password_changed_at becomes invalid.
Support must be forced to login again.
```

Unauthorized response:

```json
{
  "success": false,
  "error": {
    "code": "TOKEN_INVALIDATED",
    "message": "Your session has expired. Please login again."
  }
}
```

# 17. Web Push Notification APIs

Web Push adds an optional browser delivery channel for existing internal Notifications. It does not replace the `notifications` table and does not change notification read state. The internal Notification remains the source of truth and is still retrieved through `GET /notifications`.

Implementation policy:

- VAPID is used for Web Push authentication.
- `WEB_PUSH_ENABLED=false` returns disabled public config.
- If `WEB_PUSH_ENABLED=true`, VAPID public key, private key, and subject must be configured at startup.
- Only the VAPID public key is returned by API.
- VAPID private key is never returned, logged, or stored in the database.
- There is no queue in this repository; delivery is best effort and failures do not fail ticket operations.
- Full push endpoints and subscription keys are not returned from list APIs.

Environment:

```text
WEB_PUSH_ENABLED=false
WEB_PUSH_VAPID_PUBLIC_KEY=
WEB_PUSH_VAPID_PRIVATE_KEY=
WEB_PUSH_VAPID_SUBJECT=mailto:admin@example.com
```

## 17.6 Push Payload Schema

```json
{
  "version": 1,
  "notificationId": 3001,
  "type": "NEW_MESSAGE",
  "title": "New ticket message",
  "body": "A new reply was added to your ticket.",
  "url": "/app/tickets/101",
  "ticketId": 101,
  "createdAt": "2026-08-03T10:30:00.000Z",
  "tag": "notification:3001",
  "data": {
    "url": "/app/tickets/101",
    "notificationId": 3001,
    "ticketId": 101
  }
}
```

Payload rules:

- Payload is versioned with `version: 1`.
- URL must be relative and start with `/app`.
- If no safe ticket route exists, URL is `/app/notifications`.
- Payload does not include full message text, attachment data, usernames, personal data, full endpoint, subscription keys, or VAPID private key.
- Push delivery does not mark the internal Notification as read.

## 17.7 Notification Type Mapping

```text
NEW_MESSAGE
Recipient: USER ticket owner when Support/Admin replies
URL: /app/tickets/{ticketId}
Push body: generic new-reply text

TICKET_STATUS_CHANGED
Recipient: USER ticket owner when Support/Admin changes status
URL: /app/tickets/{ticketId}
Push body: generic status-change text

SYSTEM_NOTIFICATION
Recipient: specific USER only
URL: /app/notifications

NEW_TICKET_CREATED
TICKET_ASSIGNED
TICKET_REASSIGNED
TICKET_DEPARTMENT_CHANGED
Version-one Push delivery: disabled unless a USER-app-safe route is explicitly available
```

Support/Admin subscription storage is allowed by API design, but management-panel Push delivery is intentionally disabled in this version because the User Application is the only targeted PWA route space.

## 17.8 Delivery Failure Behavior

```text
404 / 410
Deactivate the subscription.

401 / 403
Treat as VAPID/provider auth or configuration failure. Keep subscription active.

429 / 5xx
Keep subscription active. No queue retry exists in this version.

Payload too large / timeout
Keep subscription active and record failure metadata.
```

Delivery logs must be sanitized. Allowed log fields include notification id, user id, subscription id, endpoint fingerprint, notification type, result, provider status code, and duration. Full endpoint, keys, private key, authorization header, and sensitive payload data must not be logged.
